# Desktop updates

Installed release builds check on startup and expose **Settings → Updates** for
manual checks, release notes, download progress, and installation. Installation
is explicit and restarts Slopus. Close the project and finish or cancel queued
work first; unsaved project changes or videos also block installation. Failed
checks and downloads can be retried from Settings.

Browser previews, debug builds, and portable folders containing the
`slopus-portable` marker do not check for updates. Keep that marker when moving a
portable installation. Update portable copies by downloading a new portable ZIP.

## Signing key

The public key is committed in `src-tauri/tauri.conf.json`. The matching private
key was generated locally at `%USERPROFILE%\.tauri\slopus-updater.key`, outside
the repository, without a password. Back it up securely: existing installations
trust this key, and losing it prevents signing updates they will accept. Never
commit or upload the private key as a release asset.

`release.cmd` uses this path by default. On another build machine, restore the
same key and set these environment variables as appropriate:

```powershell
$env:TAURI_SIGNING_PRIVATE_KEY = 'C:\secure\slopus-updater.key'
# Set this only if the key is password-protected:
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = 'your-key-password'
```

For a new app identity before distributing any builds, a key can be generated
with `npx tauri signer generate --write-keys C:\secure\slopus-updater.key`.
Put the complete contents of the resulting `.pub` file in `plugins.updater.pubkey`.
Do not regenerate the key for each release.

## Publish a Windows update

1. Set the same new version in `package.json`, `package-lock.json`,
   `src-tauri/Cargo.toml`, and `src-tauri/tauri.conf.json`. Update the configured
   window title too. Cargo updates its lockfile during the build.
2. Optionally set `UPDATE_NOTES_FILE` to a UTF-8 text file containing release notes.
3. Run `release.cmd`. It builds signed installers, copies their `.sig` files,
   and writes `artifacts/latest.json` with the version, signatures and download URLs.
4. Create a GitHub Release in `bitti-ai/slopus` with tag **`v<version>`**, matching
   the manifest URLs. Upload `latest.json`, the setup EXE and its `.sig`, and the
   MSI and its `.sig` if produced. Upload the portable ZIP as a separate download.
   Publish the release as the latest stable release after all assets are present.

The app requests
`https://github.com/bitti-ai/slopus/releases/latest/download/latest.json` over
HTTPS and verifies each installer with the embedded public key. These assets
must be publicly downloadable; the app does not embed GitHub credentials. Until
the first release containing `latest.json` is published, checks will report an
error and leave the current app running.

The manifest generated by `release.cmd` covers the current Windows architecture
and includes NSIS/MSI-specific targets. When publishing more architectures or
operating systems, merge their platform entries into one `latest.json` before
uploading it. Tauri also supports signed macOS and Linux updater artifacts; the
existing Windows packaging script does not build those.

`package.cmd` still builds portable binaries without bundling, so it does not
need the signing key. Direct installer builds (`npm run tauri -- build`) require
`TAURI_SIGNING_PRIVATE_KEY` in the environment.

Before public distribution, test with two installed versions: publish the newer
signed build, launch the older updater-enabled build, then check, install and
verify the restarted version. A live upgrade cannot be tested until a newer
release is hosted.

Reference: [Tauri updater documentation](https://v2.tauri.app/plugin/updater/).
